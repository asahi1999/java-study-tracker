## 1. コンセプト名と一言キャッチ

### 「Java ダンジョン工房」

**1部品5分。積み上げたら、自分のゲームが Web で動く。**

- 練習問題を「部品」と呼ぶ。部品は1個5〜15分。解くと、必ず画面に**絵・動き・表**が出る
- 部品は全部、1本の自作ゲーム『ちいさなダンジョン』のパーツになる
  - 第1部：マップを描く → プレイヤーが歩く → 壁に当たる
  - 第2部：モンスターが出る → 種類ごとに違う動きをする
  - 第3部：アイテムを集める → セーブ・ロード → ランキング
  - 第4部：Spring Boot に載せて、ブラウザで遊べる Web アプリになる
- 最後に残るのは「勉強した記録」ではなく「GitHub に置ける自分の作品」

v1 との違い（一言）：v1 は「やったことを記録する」アプリ。今回は「開いたらそのまま Java を書いて、動くものが出てくる」アプリ。記録は自動で裏側に残すだけにする。

## 2. 体験の流れ

### 2-1. 初回起動（5分）

1. URL を開く。v1 のデータがあれば「v1 の学習記録 23時間 を引き継ぎました」とだけ出す。設定画面や目標入力は**出さない**
2. いきなり最初の部品「0-1 画面に色を置こう」が開く
   - エディタに3行だけのコードが入っている
   - 「▶ 実行」を押すと、右のキャンバスに 8×8 マスの黄色い点が2つ出る
3. 「`"#f5c542"` を `"#40a0ff"` に変えてもう一度」と出る。変えて実行すると青になる
4. 次の部品 0-2 で `for` を1行足すと、点が横一列の線になる。顔の絵ができる
5. 完成した絵が「ギャラリー」に1枚目として飾られる。部品図鑑に「for文 ―― くりかえし装置」のカードが入る
6. ここで初めて「工房」（ホーム画面）を見せる。真ん中に『ちいさなダンジョン v0.0（まだ何もない）』の空っぽの画面がある

→ **起動から最初の「動いた」まで2分以内**。VS Code の準備は、最初の「組み立て」（1章の終わり）まで求めない。

### 2-2. 1回の学習セッション

#### 平日の夜、15分だけのとき

1. PC を開き、Dock の PWA アイコンをクリック
2. ホームの大きなボタン「▶ つづきから：3-4 ジグザグ模様を描く（約8分）」を押す。**選ぶ手間ゼロ**
3. 冒頭30秒の「ウォームアップ」：前回作った模様がもう一度描かれ、数字を1つ変えるだけの問題
4. 本題の穴埋め。2回失敗すると、ヒントボタンの横に「質問カードを作る」が光る（6-7 参照）
5. 正解すると模様がアニメーションで描かれ、「部品 +1／工房レベル 4 まであと 30XP」
6. 次の部品の**予告**が出る：「次：この模様を迷路の壁にする」。ここでやめてもよいし、続けてもよい
7. 閉じるだけ。学習時間は自動で記録される（タイマー操作なし）

#### 休日、1時間以上あるとき

1. ホームで「今日の持ち時間」を押すと「5分／15分／30分／1時間以上」が出る（押さなくてもよい）
2. 「1時間以上」を選ぶと「組み立て 4：迷路を歩くプレイヤー（約50分・チェックポイント3つ）」を提案
3. 「VS Code で始める」を押す
   - フォルダ連携済み（Chrome）なら、課題ファイルがワークスペースに自動で書き込まれる
   - 未連携なら、初回に配った `java-quest` フォルダの `ch04/` を開くだけ（ファイルは最初から全部入っている）
4. VS Code で `ch04/Walk.java` を書き、`Cmd+Shift+B`（タスク登録済み）を押す
5. ターミナルに色付きのマスで迷路が描かれ、テスト結果とクリアコード `04-2/3-K7QF` が出る
6. アプリに戻ると、フォルダ連携済みなら結果を自動で読み込む。未連携ならクリアコード（11文字）を貼るだけ
7. チェックポイント2まで終わったところで用事ができても、続きはチェックポイント3から再開できる
8. 組み立てを完了すると、ホームの『ちいさなダンジョン』が v0.4 に上がり、**自分で書いた歩行ロジックで**キャラが歩くようになる

### 2-3. 1ヶ月後（2026年12月末）

- 第1部（基礎）が終わり、第2部の途中。ホームのダンジョンには、マップ・プレイヤー・壁・ゴールがある
- 年末に2週間まったく開かなかった。開くと：
  - 「おかえり。前回はここまで」と、最後に作った絵（ギャラリーの最新）が出る
  - 「1分ウォームアップ」（前回の部品の超短縮版）→ そのまま続きへ
  - 「遅れ」「連続記録が途切れた」は**どこにも出ない**
- 完走見込みは、設定画面の奥にだけある：「このペースなら 2/20 ごろ完走（3月は丸ごと予備）」
- 遅れているときは、各章の「おかわり部品」が自動で「あとで」に回り、必須ルートだけが残る。ユーザーには「近道ルートに切り替えました。おかわりは図鑑からいつでも遊べます」と1回だけ伝える

### 2-4. 完走（2027年2月）

- 第4部で、手元の Spring Boot アプリが起動する。`http://localhost:8080` を開くと、これまで作ったマップ・モンスター・アイテム・ランキングが入ったダンジョンがブラウザで遊べる
  - サーバー側の Java（Controller・Service・ゲームロジック）は全部自分のコード
  - 画面の HTML/JS は配布する（Java の学習に集中するため）
- 最後の部品は「README を書いて GitHub に push する」。アプリが README の下書き（使った技術、章ごとに学んだこと、ギャラリーの画像）を出力する
- 工房には「完成品」として作品のスクリーンショットと、全部品の図鑑が並ぶ
- 3月は予備。おかわり章（DB・JUnit・ジェネリクス）で、研修「Java上級」に備える

## 3. 4つの壁への効き方

| 壁                               | 効く仕組み                                                                                                                                                                                                                                                  | なぜ効くか                                                                                                      |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **1回が重い**                    | ・1部品5〜15分、最小単位は5分<br>・ホームの「▶ つづきから」1ボタンで、エディタにコードが入った状態から始まる<br>・冒頭30秒のウォームアップは「数字を1つ変えて実行」だけ<br>・組み立て（長い課題）も15〜20分のチェックポイントに分割                         | 「勉強を始める」ではなく「ボタンを1つ押す」まで入口を小さくする。始めてしまえば続く                             |
| **何から手をつけるか分からない** | ・次にやる部品は常に1つだけ表示（迷わせない）<br>・持ち時間を選べば、その時間に合う1つを提案<br>・全体図は「ダンジョンの完成図」で見せる。今どのパーツを作っているかが分かる                                                                                | 選択肢を出さない。「次の1手」と「それが何の部品になるか」だけ見せる                                             |
| **スマホや遊びに流れる**         | ・実行から結果まで1秒前後。絵や動きがすぐ出る<br>・部品の終わりに次の部品の「予告」（次はこのスライムを動かす）<br>・やめても罪悪感が出ない（連続記録なし・遅れ表示なし）ので、戻ってきやすい<br>・途中のコードは自動保存。スマホを触っても、戻れば同じ画面 | アプリはスマホを止められない（8章の弱点を参照）。代わりに「スマホより先に結果が出る」「戻るコストがゼロ」にする |
| **Java が面白くない**            | ・コンソールに文字を出すだけの問題を置かない。全部品が絵・動き・表を出す<br>・題材は1本のゲームに統一。書いたコードがホームのゲームに反映される<br>・第4部で「自分のゲームが Web で動く」というゴール                                                       | 「Java の文法を覚える」を「自分のゲームの部品を作る」に置き換える                                               |

## 6. 学習コンテンツの形式

### 6-1. 問題の種類

| 種類         | 所要時間 | 内容                                                                 | ブラウザ実行なしでも成立するか                         |
| ------------ | -------- | -------------------------------------------------------------------- | ------------------------------------------------------ |
| いじって実行 | 2〜5分   | 動くコードの数字や色を変えて、結果の変化を見る。ウォームアップに使う | △ 値をスライダーで選ぶ形に変え、事前計算した結果を描く |
| 予想         | 1〜2分   | 実行前に「どの絵になるか」を3枚から選ぶ                              | ◯ そのまま                                             |
| 穴埋め       | 5〜10分  | 1〜3か所を埋めて実行。隠しテストで判定                               | △ 選択肢式、または決まった答えとの文字列比較           |
| 並べ替え     | 3〜5分   | バラバラの行を正しい順に並べる（Parsons 問題）                       | ◯ そのまま                                             |
| バグ直し     | 5〜10分  | 動かない（変な絵になる）コードを直す                                 | △「どの行がおかしいか」を選ぶ形に変える                |
| 自由に描く   | 5〜15分  | 正解なし。何を描いてもギャラリーに入る                               | ✕ → 手元の「らくがき帳」ファイルに回す                 |
| 組み立て     | 30〜60分 | VS Code で書く。チェックポイント2〜4個（各15〜20分）                 | ◯ もともと手元で実行                                   |

- 1章あたり：いじって実行1・予想1〜2・穴埋め2〜3・並べ替えかバグ直し1・組み立て1
- 判定はすべて「出力された行」で行う。ブラウザでも手元でも同じ判定ロジックを使える

### 6-2. 見た目を出す仕組み：`Stage` クラス

全部品で使う小さな描画クラス。学習者は最初、中身を知らずに使う。7章で「クラスの例」として中身を読む。

- ブラウザで動かすとき：`@cell x y 色` の行を出し、アプリがキャンバスに描く
- 手元で動かすとき：ターミナルに色付きの四角（ANSI エスケープ）で描く。VS Code のターミナルで色が出る
- ブラウザ実行の技術が何であっても、標準出力さえ取れれば動く

```java
public class Stage {
    /** ブラウザで実行するとき、アプリ側が true にする */
    public static boolean browser = false;

    private final int w;
    private final int h;
    private final String[][] cells;

    public Stage(int w, int h) {
        this.w = w;
        this.h = h;
        this.cells = new String[h][w];
    }

    /** (x, y) のマスを塗る。はみ出したら何もしない（初心者がつまずかないように） */
    public void fill(int x, int y, String color) {
        if (x < 0 || x >= w || y < 0 || y >= h) {
            return;
        }
        cells[y][x] = color;
    }

    public void clear() {
        for (String[] row : cells) {
            java.util.Arrays.fill(row, null);
        }
    }

    /** 今の状態を1コマとして出す。何回も呼ぶとアニメーションになる */
    public void show() {
        if (browser) {
            printForBrowser();
        } else {
            printForTerminal();
        }
    }

    private void printForBrowser() {
        System.out.println("@stage " + w + " " + h);
        for (int y = 0; y < h; y++) {
            for (int x = 0; x < w; x++) {
                if (cells[y][x] != null) {
                    System.out.println("@cell " + x + " " + y + " " + cells[y][x]);
                }
            }
        }
        System.out.println("@end");
    }

    private void printForTerminal() {
        StringBuilder sb = new StringBuilder();
        for (int y = 0; y < h; y++) {
            for (int x = 0; x < w; x++) {
                String c = cells[y][x];
                if (c == null) {
                    sb.append("  ");
                    continue;
                }
                int rgb = Integer.parseInt(c.substring(1), 16);
                sb.append("\u001B[48;2;%d;%d;%dm  \u001B[0m"
                        .formatted(rgb >> 16, (rgb >> 8) & 0xff, rgb & 0xff));
            }
            sb.append('\n');
        }
        System.out.print(sb);
    }
}
```

- 第3部では同じ仕組みで `Chart`（棒グラフ：`@bar ラベル 値`）を追加する
- ブラウザでは、学習者に見せるのは `main` の中身やメソッドだけ。アプリが見えない部分（クラスの外枠、`Stage.browser = true`、隠しテスト）を足してから実行する。ブラウザ側の Java が古い版でも、外枠をアプリが作るので問題にならない

static String clearCode(int chapter, int passed, int total) {
    String body = "%02d-%d/%d".formatted(chapter, passed, total);
    int h = Math.floorMod((body + ":jq").hashCode(), 36 * 36 * 36 * 36);
    String check = Integer.toString(h, 36).toUpperCase();

}

### 7-1. 難しさ

| 部分                          | 難しさ               | 理由・対策                                                                                                                                 |
| ----------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |

- CI で、全部品の模範解答を JDK 25 で実行し、判定に通ることを確認する。「教材のテスト」が自動で回る

### 7-2. MVP の範囲

目標：**開発1〜2週間で、第1部の前半（0〜3章）を遊べる状態**。残りの章は、学習の進みより先に足していく。

MVP に入れるもの

- ホーム（つづきから・ダンジョンの完成度・工房レベル）
- 部品プレイヤー（エディタ・実行・判定・ヒント・`Stage` 描画・アニメーション）

- 質問カード
- 学習時間の自動記録、おかえり画面
- v1 データの引き継ぎ、エクスポート／インポート、PWA
- コンテンツ：0〜3章（部品 約25個、組み立て4個 ≒ 7.5時間分。週3時間でも2週間以上もつ）

MVP の後

- 4章以降のコンテンツ（2週間分ずつ先回りで追加）
- フォルダ連携、ホームで自作ゲームを遊ぶ画面、復習カード、改造チャレンジ、README 下書き出力

## 8. この案の弱点（正直に）

1. **コンテンツを作るのが重い**
   - 約100部品すべてに「絵が出る」仕掛けが要る。問題を作る側の負担が、ほかの案よりはっきり大きい
   - 先回りでの追加が遅れると、学習が止まる。いちばんの失敗パターン
2. **アプリ開発そのものが、勉強からの逃げ道になりうる**
   - 本人が作るアプリなので、「アプリを直している時間」が「Java を勉強している時間」を食う。しかも開発は TypeScript
   - 対策案：MVP を小さく切る。コンテンツ作りは Claude Code に任せ、本人は模範解答を見ない
3. **ネタバレ**
   - 本人が開発者なので、リポジトリを見れば答え（`Solution.java`）が見える。見ない、と決めるしかない
4. **`Stage` は自作の API**
   - 実務では使わない。「Java の標準ではない書き方に慣れる」リスクがある
   - 対策：使うのは `fill` と `show` くらいに絞る。7章で中身を読ませ、ただの Java のクラスだと理解させる
5. **ゲームの題材が合わない可能性**
   - ダンジョンが子どもっぽい、または興味がわかないと、全部の動機づけが崩れる。題材が1本なので、差し替えがききにくい
   - 研修「Java上級」は業務寄り（DB・設計・テスト）の可能性が高い。ゲーム題材ではそこが薄く、おかわり章頼み
6. **「自分のゲーム」感が薄くなるおそれ**
   - 初心者に1本のゲームを作らせるには、配布するコード（外枠・画面・隠しテスト）が多くなる。自分で書いた割合が3割程度だと「作らされている」感じが出る
7. **ブラウザ実行がない、または遅い場合**
   - 代替モードの部品は選択式が中心になり、「自分で書いて動いた」感覚が弱まる。この案の売りがいちばん落ちる
   - 起動に数秒以上かかる技術だと「すぐ結果が出る」が崩れる
   - ホームで自作ゲームを遊ぶ画面は、ブラウザ実行がないと作れない（JavaScript で作った見本になってしまう）
8. **スマホは止められない**
   - 静的サイトにできるのは「戻ってきやすくする」まで。スマホに流れること自体は防げない
9. **Spring Boot の最初の起動が重い**
   - Maven の依存ダウンロードで数分かかる・失敗する、が起きると、その回だけ「1回が重い」に逆戻りする
   - 対策：13章の最初の部品を「`./mvnw` を動かして待つだけ（ダウンロード中に解説を読む）」にする
10. **使うブラウザが不明**
    - フォルダ連携は Chrome / Edge のみ。普段 Safari なら、クリアコード貼り付けが常に必要になる
