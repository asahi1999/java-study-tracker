## 0. 結論（先に）

- **どの案も、そのままでは完成しない。原因はアプリではなく教材の量と、その正しさの確認**
  - A: 約130問＋ボス9体（区画27）。B: 約200問＋工作9本＋選択肢ごとの解説。C: 約100部品＋組み立て17本＋事前計算
- **3案とも「ブラウザで Java が動かない場合」の代わりの教材を問題ごとに持つ前提。これはやめる**
  - 調査で teavm-javac が動くと分かった。問題ごとに2つの形を作ると、教材の作業が倍になる
  - 代わりの手段は「手元で実行して結果を貼る」の1つだけにする。全問題に同じ仕組みで使える
- **推奨の組み合わせ**
  - 骨格は B（開いたらすぐ1問、短い問題）
  - 見た目は A（テストが通ると灯りがともる、文字の出力をタイルで描く、エラーの説明）
  - 手元の課題は C（作業フォルダの zip、`Check.java`、クリアコード、1本の作品に育つ）
- **品質を保てる量**: 本線は小問 約110問＋手元課題 8本＋Spring Boot 1本。MVP は第0〜2章（小問 約30問＋手元課題 2本）
- **最初にやること**: Safari を含む対応ブラウザの確認と、教材を自動で確かめる仕組み（CI）。画面より先

## 1. この評価で追加で実測したこと

場所: `scratchpad/critic/`（`~/java-study-tracker` は変更していない）。JDK 25.0.5（Temurin）、Node 24.15.0、調査で取得した teavm-javac（playground/4）を使用。

## 2. 各案の実装リスク

### 2-1. 3案に共通するリスク

- **教材が先に尽きる**
  - 週3時間だと1章が約1週間で終わる。教材の追加が遅れると、解く問題がなくなって離脱する（B・C も自分で書いている）
  - 対策: 常に2章先まで教材を作っておく。章ごとに CI で確かめてから公開する
- **ネタバレ**
  - 利用者が開発者でもある。リポジトリ・プルリクエスト・エージェントの返答に模範解答が出る
  - 対策
    - 教材のプルリクエストの説明やエージェントの返答には、問題の中身を書かない（「第2章 12問追加、CI 全通過」程度）
    - 本人は教材の中身を確認しない。正しさは CI とレビュー用エージェントで確かめる
    - 模範解答は別ファイルにし、クリア後に読み込む（隠すためではなく、うっかり見ないため）
- **本番で確かめる手段がない**
  - main に push すると本番に出る。revamp ブランチは GitHub Pages で試せない
  - GitHub Pages の gzip・Service Worker の範囲・wasm のキャッシュは、本番で初めて確かめることになる
  - 対策: v1 のデータを壊さない移行にする（5章）。問題が出ても v1 に戻せる
- **Safari で動くか分からない**
  - 調査で動作を確かめたのは Chrome と Node だけ。WasmGC は Safari 18.2 から対応（調査より）
  - teavm-javac がどの例外処理の方式を使うかは未確認。Safari で動かない可能性がある
  - 対策: 実装の最初に、調査のテストページを利用者の Mac の Safari・Chrome で開いて確かめる。CI では Playwright の WebKit で確かめる（Safari と完全に同じではない）
- **同じオリジンを共有している**
  - `asahi1999.github.io` の IndexedDB・localStorage・Cache Storage は、利用者のほかの GitHub Pages サイトと同じオリジンになる
  - 対策: DB 名やキャッシュ名に `java-study-tracker` を付ける。Service Worker の範囲は `/java-study-tracker/` に限る
- **予想した出力を入力する問題で、日本語入力（IME）の全角が混ざる**
  - 例: A の `合計: 72` を `合計：72` と打つと不正解になる
  - 対策: 比べる前に NFKC で正規化し、行末の空白を無視する。違う行は差分で見せる。迷う問題は選択式にする

### 2-2. A（灯台守）

- 技術
  - **エラー図鑑**: 実行時の例外メッセージに頼ると、ブラウザでは null になる（実測）。例外の型と、コンパイルエラーの英語・日本語の文言で判定する
  - **出力をタイルで描く**: 文字と絵の対応表と CSS グリッドで済む。手元のターミナルでも同じ文字が出る。**3案の見た目の仕組みで最も簡単で壊れにくい**
  - **港町マップ**: 絵を誰が描くかが問題。エージェントが描くイラストは質が安定しない。ポートフォリオとして見劣りする危険がある。最初は単純な図形（SVG・CSS）にする
  - **最終章で localhost の Spring Boot に接続**: https のページから `http://localhost` への接続は、ブラウザのローカルネットワークへのアクセス制限にかかる可能性がある。ブラウザごとの挙動に**自信がない**。A 自身の代案（Spring Boot 側で画面を出す）を本命にする
  - 第7章のファイル入出力はブラウザで動かない（実測）。手元専用にする
- 教材
  - ボス9体×3区画で `Check.java` が27段階。区画ごとのテストも要る
  - 「同じ問題に8分いたら狼煙」などの時間の計測は、画面が見えている間だけ数える必要がある（v1 のタイマーと同じ問題）
- テストのしやすさ
  - タイル描画・判定・合言葉は純粋関数でテストしやすい。港町マップの見た目はスナップショット程度しかできない

### 2-3. B（ひとくち Java）

- 技術
  - 実行しない形式が中心なので、**技術のリスクは3案で最も低い**
  - **並べ替え問題を「行の順番」で判定すると、正しい並べ方が複数ある問題で誤判定になる**。組み立てたコードを実行して判定する
  - **数字違いの問題（バリエーション）**: テンプレートから作ると、変形ごとの正解を JDK で確かめる仕組みが要る。MVP では作らない。必要なら、作るときに別の問題として書き出して CI で確かめる
  - **難易度の自動調整（85% ルール）**: 問題ごとの難しさの数値をあらかじめ正しく付けられない。調整しても効いているか確かめられない。やめる
  - 「書く」問題の自己採点は、teavm-javac を入れるなら要らない。テストで判定する
- 教材
  - **選択肢ごとの解説（200問 × 誤答3つ）が、自動で確かめられない文章として一番多い**
  - 自動で確かめられるのは「誤答の選択肢が、本当の出力と違うこと」まで。「A を選んだ人はこう考えた」という解説の正しさは確かめられない
  - 解説は「正解の理由」1つを基本にし、選択肢ごとの解説は、よくある勘違いのものだけに絞る
- テストのしやすさ
  - ライトナー方式・復習の上限・完走見込みは純粋関数。v1 の `lib/` と同じ作り方でテストできる
  - 間隔反復は「問題 ID が変わらない」ことが前提。教材を直したときに ID を変えない決まりが要る

### 2-4. C（ダンジョン工房）

- 技術
  - **`Stage` と `@cell` の出力の決まり**: 動くことは確かめた（1章）。ただし、標準ではない API を両方の実行環境と手元に配り続ける必要がある。学習者が `@` で始まる行を出すと誤判定する
  - **選択肢ごと・スライダーの全組み合わせ（64通り）の事前計算**: teavm-javac が動くなら要らない。やめる
  - **ホームで自作ゲームを遊ぶ画面**: キーボードで操作するには、Java と JavaScript をつなぐ仕組みが要る。teavm-javac で学習者のコードから使えるかは未確認。「移動の文字列を入れて再実行」までにする
  - **`Thread.sleep` でコマ送り**: teavm-javac では `main` が途中で戻る（調査より）。コマは出力から取り出し、アプリ側で再生する
  - 第11章のファイル入出力はブラウザで動かない（実測）
  - 学習者のファイルに `package ch08;` が必要。初心者には余計な1行。章ごとに `Check08.java` を同じフォルダに置く方が簡単
  - 第4部の「配布する画面の HTML/JS」は、Java と別に保守するものが増える
  - JDK 25 に対応する Spring Boot の版は**自信がない**（4.0 系なら対応しているはずだが未確認）。第4部を作る前に確かめる
- 教材
  - 17章×部品6個＋組み立て17本。全部品に絵が出る仕掛けが要り、**3案で最も重い**
  - 「MVP の開発1〜2週間」は楽観的。実行の仕組み・教材の CI・移行・PWA だけで、画面より時間がかかる
- テストのしやすさ
  - `@cell` の解析と描画は純粋関数でテストしやすい。アニメーションとキャンバスは目で見るしかない

## 3. 教材の量と、正しさを自動で確かめる方法

### 3-1. 現実的な量

- 学習者の本当の所要時間は、作り手の見積もりの1.5〜2倍になりやすい（経験則。数値の根拠は**自信がない**）。最初は少なめに作り、実際にかかった時間で次の章の量を決める
- 提案（本線）

| 種類                                 | 量                                                  | 1つの目安（失敗を含む） | 合計           |
| ------------------------------------ | --------------------------------------------------- | ----------------------- | -------------- |
| 小問（予想・穴埋め・修理・実装・絵） | 約110問（1章 10〜12問 × 第0〜8章＋第9章の確認問題） | 6〜8分                  | 11〜15時間     |
| 手元課題（第1〜8章）                 | 8本（各2〜3段階）                                   | 60〜90分                | 8〜12時間      |
| Spring Boot（第9章）                 | 1本（4〜6段階）                                     | 4〜5時間                | 4〜5時間       |
| 説明カード・復習                     | —                                                   | —                       | 4〜5時間       |
| 合計                                 |                                                     |                         | **27〜37時間** |

- 週3時間×13週＝39時間に収まる。余れば「おかわり」に回す（足りないより余る方がよい）
- **「品質を保てる量」の上限は、この 110問＋10本 程度と考える**。それ以上は自動で確かめられない文章（解説・ヒント）の確認が追いつかない
- MVP は第0〜2章（小問 約30問＋手元課題 2本）。利用者が第1章を終える前に第3章を足す

### 3-2. 1問ごとに CI で確かめること

| 確かめること                         | 方法                                                                                                                                                                                                                                                            |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 模範解答がテストに通る               | 手元と同じ JDK 25（`actions/setup-java` の temurin 25）で実行                                                                                                                                                                                                   |
| ブラウザでも同じ結果になる           | 同じ模範解答を teavm-javac（Node、問題ごとに別プロセス）で実行し、**JDK と出力が完全一致**することを確かめる。違えば CI を落とす。ブラウザで動かせない問題は `runtime: local` と書く                                                                            |
| 予想問題の正解                       | 正解は手で書かず、JDK の出力と照合する。`--update` で書き直し、差分をレビューする                                                                                                                                                                               |
| ひな形のままでは通らない             | ひな形（`Starter.java`）で実行し、**少なくとも1つのテストが落ちる**ことを確かめる                                                                                                                                                                               |
| テストが弱すぎない                   | よくある間違いの解答（`wrong/*.java`、1問2つ以上）を置き、**全部テストで落ちる**ことを確かめる（簡易なミューテーションテスト）                                                                                                                                  |
| 修理問題は本当に壊れている           | 壊れたコードが、書いてあるとおりのエラー（コンパイルエラーか、例外の型か、テスト失敗か）になることを確かめる                                                                                                                                                    |
| 誤答の選択肢                         | 選択肢の出力・コードが、正解と本当に違うことを確かめる                                                                                                                                                                                                          |
| 穴埋めの別解                         | 認める答えの一覧を、すべて実行してテストに通ることを確かめる                                                                                                                                                                                                    |
| 並べ替え                             | 正解の並びとダミーの行を入れた並びを実行し、前者は通り、後者は落ちることを確かめる                                                                                                                                                                              |
| 結果が毎回同じ                       | 2回実行して出力が同じこと                                                                                                                                                                                                                                       |
| JDK と違いが出る書き方を使っていない | 禁止リストで検査: `HashMap`/`HashSet`/`Map.of`/`Set.of` の中身をそのまま表示、`Random`/`Math.random`、`getMessage()` の表示、`%e`、`Files`/`FileReader`/`System.in`、`Object` の既定の `toString`/`hashCode`、`currentTimeMillis`/`now()`、`System.getProperty` |
| まだ習っていない文法を使っていない   | 章ごとに使ってよいキーワード・API の一覧を持ち、ひな形と模範解答を検査（正規表現で簡易に）                                                                                                                                                                      |
| 時間切れにならない                   | 各実行に上限（例: 10秒）                                                                                                                                                                                                                                        |
| 問題データの形                       | Zod で検査。ID の重複・章の順番・必須項目                                                                                                                                                                                                                       |
| 手元課題                             | 模範解答を入れた作業フォルダで `java Check.java` を実行し、全段階のクリアコードが出ることを確かめる。ひな形のままでは出ないことも確かめる                                                                                                                       |
| Spring Boot                          | 模範解答のプロジェクトで `./mvnw test`。重いので、そのフォルダが変わったときだけ動かす                                                                                                                                                                          |

- 自動で確かめられないもの（問題文・解説・ヒントの日本語、教え方の順番）
  - 作ったエージェントとは別のエージェントが、チェックリストでレビューする
  - チェック項目: 問題文だけで解けるか、ヒント3段目が答えそのものになっていないか、解説が出力と矛盾しないか、まだ習っていない用語を使っていないか
  - 問題データに `reviewed: true` を付け、付いていない問題は公開しない
- 利用者が「この問題おかしい」と思ったとき
  - アプリに「問題を報告」ボタンを置き、GitHub の Issue 作成画面を、題名と本文を入れた URL で開く（API は使わない。送るのは利用者）
  - 本文には問題 ID と自分のコードを入れる。模範解答は入れない
- CI の時間の見積もり
  - 1問あたり: 模範解答＋ひな形＋間違い2つ＝4回 × 2環境。teavm-javac は1回 約2秒（実測）、JDK は 0.5〜1秒
  - 110問で 20〜30分（順番に実行した場合）。並列にする、教材が変わったときだけ動かす、で10分以内に抑える
  - `npm test` とは分け、`npm run content:verify` にする（JDK が必要なため）。CI では両方動かす

## 4. teavm-javac を本番に入れるときの課題と対策

### 4-1. リポジトリに入れるか、取得スクリプトにするか

- **推奨: リポジトリに入れる**（`public/java/teavm-javac/<版>/`）
  - 理由
    - ビルドや CI が teavm.org の稼働に左右されない
    - `playground/4/` の中身が予告なく変わる可能性がある（調査で README の案内先が古い版だったことも分かっている）
    - サイズは約7.6MB。現在の `.git` は 2.7MB。更新は年に数回の想定なので、履歴が増えても問題にならない
  - Git LFS は使わない（GitHub Pages の Actions で取得の設定が要る、無料枠の転送量がある）
- 付けるもの
  - `SHA256SUMS`: 全ファイルのハッシュ。CI で毎回照合する
  - `SOURCE.md`: 取得元 URL、取得日、teavm-javac のコミット、TeaVM の版、OpenJDK（jdk25u）のタグ
  - `scripts/fetch-teavm-javac.mjs`: 更新するときだけ使う取得スクリプト（ハッシュを表示する）。ビルドでは使わない
- **Scanner の代わりのクラスを足した `compile-classlib` は、自分で作るファイル**
  - 代わりのクラスのソースと作るスクリプトをリポジトリに置き、CI で作り直してハッシュが一致することを確かめる
  - gzip は時刻をヘッダーに入れるので、`mtime=0` にしないと毎回中身が変わる
- 余力があれば: teavm-javac をソースからビルドするワークフロー（Java 21 と Gradle が必要。調査では未実施）

### 4-2. ライセンス表記

- 置くもの
  - `THIRD_PARTY_NOTICES.md`（README からリンク）と、アプリの「ライセンス」画面
  - TeaVM・teavm-javac: Apache License 2.0 の全文（NOTICE があればそれも）
  - OpenJDK（javac 部分）: GPLv2 + Classpath Exception の全文と、対応するソースへのリンク（teavm-javac のコミットと jdk25u のタグ）
  - deobfuscator.wasm（Maven から取得）: Apache License 2.0
- 注意
  - GitHub の API では teavm-javac のライセンス欄が空（調査より）。実装時に LICENSE ファイルがあるかを確かめ、無ければ README の記載を根拠として `SOURCE.md` に書く
  - javac をバイナリで配るので、GPLv2 のソース提供の条件がかかると考えられる。リンクで足りるかの法的な判断は**自信がない**
  - **このリポジトリ自体に LICENSE ファイルがない**。第三者のコードを同梱する前に、自分のコードのライセンス（例: MIT）を決める。利用者の判断が必要

### 4-3. サイズと読み込み

- 合計 約7.6MB（gzip なら約4.5MB）。GitHub Pages が `.wasm` を gzip で返すかは未確認。最悪 7.6MB と考える（PC の回線なら許容範囲）
- 読み込みの順番
  - ホーム画面の表示では読み込まない
  - 表示が終わってから、コンパイル用の Worker を裏で起動しておく（最初の「実行」で待たせない）
  - 初回のダウンロード中は進み具合を出す
- PWA
  - vite-plugin-pwa（Workbox）は既定で 2MiB を超えるファイルをキャッシュしない。`maximumFileSizeToCacheInBytes` を 10MB に上げる
  - ファイルの場所に版を入れる（`/java/teavm-javac/0.17.0-pg4/`）。更新時に古いキャッシュと混ざらない
  - Service Worker の更新は「確認してから」（`registerType: 'prompt'`）にする。書いている途中で勝手に再読み込みしない
- `.wasm` は ArrayBuffer で取得して渡す（調査の推奨どおり。MIME に依存しない）

### 4-4. Web Worker での実行と時間切れ

- Worker を2つに分ける（調査どおり）
  - コンパイル用: 常駐。javac＋TeaVM の Wasm 生成。15秒で応答がなければ作り直す。コンパイラ内部の Wasm エラーのときだけ、作り直して1回やり直す（学習者のコードのエラーではやり直さない）
  - 実行用: 毎回新しく作る。時間切れ（既定 3秒、問題ごとに最大10秒）で `terminate()`
- 決めておくこと
  - 出力の上限（例: 100KB または 2,000行）。超えたら止めて「出力が多すぎる（無限ループかも）」と出す
  - 出力は Worker 内でまとめて 50ms ごとに送る（1文字ずつ送ると画面が固まる）
  - 実行中にもう一度押されたら、前の実行を止めてから始める
  - `RangeError` →「StackOverflowError（再帰が深すぎる）」と表示
  - メモリ不足の Wasm エラー →「メモリが足りない（配列が大きすぎるかも）」
  - TeaVM 内部のスタックトレースの行（`org.teavm.`）は消す
  - 終了の検出は、ラッパーの最後の `System.exit(0)` と `onExit`（調査どおり）
- テスト
  - jsdom では Worker と Wasm を動かせない。実行の中心部分（コンパイル・実行・出力の整形）は Worker から切り離し、Vitest の Node 環境で本物の teavm-javac を使ってテストする
  - Worker を含む通しのテストは Playwright（Chromium と WebKit）で数問だけ動かす
  - 画面のテストでは `JavaRunner` を偽物に差し替える

### 4-5. JDK との違いの扱い

- 方針: **「ブラウザで動かす問題は、JDK と同じ出力になるものだけ」にする**
  - 違いの出る書き方は、作るときの禁止リスト（3-2）と CI の比較で防ぐ
  - どうしても使う内容（ファイル入出力、本物の標準入力、`HashMap` の表示順の話）は手元の課題にする
- 標準ライブラリは Java 21 相当として扱う（実測で `java.version` が 21）。Java 22 以降の API は使わない。文法は Java 25 でよい
- 画面での扱い
  - すべての問題に「手元で実行」ボタンを置く。判定用のクラスを含めた1ファイルをコピーできる
  - 実行結果の下に小さく「ブラウザの Java は本物と細部が違うことがある。おかしいと思ったら手元で」と出す
  - 実行時の例外は、型と日本語の説明を出す。メッセージが null のときは表示しない

## 5. 「手元で実行して合言葉を貼る」の作り方と、不正の扱い

### 5-1. 作り方

- 作業フォルダ（`java-quest.zip`）
  - CI で作り、GitHub Pages に置く。全章のひな形・判定用のクラス・`.vscode/tasks.json` を入れる
  - zip の中に教材の版を入れる。`Check.java` が版を表示し、アプリの版と違えば「新しい作業フォルダがあります」と出す
  - 再ダウンロードで自分のコードを上書きしないよう、章ごとの zip も用意する
- 判定（`Check.java`）
  - 章ごとに同じフォルダに置く（`ch03/Check.java`）。`package` 宣言を学習者に書かせないため
  - 結果は人が読める行＋最後の1行にクリアコード
- クリアコード
  - 形: `JQ1-<問題ID>-<通過数>/<全体>-<確認用4文字>`
  - 確認用の文字は、FNV-1a（32bit）で `問題ID|通過数|全体|教材の版` から計算した値の36進数4桁。Java と TypeScript の両方で書ける（`Math.imul` で同じ計算になる）
  - 問題 ID は英数字に限る（文字コードの違いで計算がずれないように）
  - 同じテスト用データ（入力と期待するコードの組）を、Vitest と CI の Java の両方で確かめる
- アプリへの戻し方（簡単な順）
  1. クリアコードを貼る（MVP）
  2. ターミナルの出力をまるごと貼る（MVP）。アプリが PASS/FAIL の行を読み、途中の段階も記録する。失敗した行は「質問文」にそのまま入れられる
  3. `Check.java` が `https://asahi1999.github.io/java-study-tracker/#/clear/<コード>` を表示し、VS Code のターミナルで Cmd+クリックして開く（余力があれば。PWA とブラウザのタブは同じ IndexedDB を使う）
  4. File System Access API で作業フォルダを直接読む（余力があれば。Chrome・Edge のみ）

### 5-2. 不正（答えを見る）をどこまで気にするか

- **防がない**。利用者は本人1人で、だまして得をする相手がいない
  - クリアコードは打ち間違いを防ぐためだけのもの
  - 暗号化や難読化は、作る量とテストが増えるだけで効果がない
- 気にするべきなのは「うっかり見てしまう」と「記録がうそになる」の2つ
  - うっかり: 模範解答は、クリア後か「答えを見る」を押したときだけ読み込む。リポジトリ・プルリクエストに中身を書かない（2-1）
  - 記録: 「答えを見た」「ヒント3段目を見た」を、罰なしで記録する。そうした問題は早めに復習に回し、完走見込みの計算にも使う

## 6. v1 からの移行

### 6-1. 技術スタック

- **続ける**: React 18 + TypeScript + Vite + Tailwind 3 + Dexie + Zustand + Vitest + Zod、ESLint・Prettier・CI の設定、テストの準備（`tests/setup.ts`、fake-indexeddb）
  - 理由: テストと CI がすでに整っている。ポートフォリオとして続いている方が説明しやすい。React 19・Tailwind 4 への更新は目的に関係なく、作業とリスクが増えるだけ
- **足す**: CodeMirror 6（Java のハイライト）、vite-plugin-pwa、Playwright（開発用）、教材の Markdown の前書き（frontmatter）を読むライブラリ（例: `yaml`）
- **外す候補**: recharts（統計画面を作らないなら）、react-markdown（教材の Markdown をビルド時に HTML にするなら）
- **v1 の画面とロジックの大半（ロードマップ編集・タイマー・連続日数・遅れの警告）は消すことになる**。消す範囲は実装前に一覧にして、利用者の確認を取る
  - 使い回せるもの: `lib/date.ts`、`lib/backup.ts` の作り方、`db/persistence.ts`、テーマ（`lib/theme.ts`・`hooks/useTheme.ts`）、`components/ui/` の一部

### 6-2. データ

- **推奨: 新しい DB（`java-study-tracker-v2`）を作り、v1 の DB（`java-study-tracker`）は読むだけにする**
  - 同じ DB の版を上げる方法（Dexie の `version(2)`）は使わない
    - 一度 v2 で開くと、v1 のアプリでは開けなくなる（版が下がるため）。本番で問題が出たとき v1 に戻せない
  - 手順
    1. 起動時に v2 の DB に「移行済み」の印があるか見る
    2. 無ければ v1 の DB を v1 のスキーマで開き、v1 の `backup.ts` の Zod スキーマで検査する
    3. 変換する関数（純粋関数）で v2 の形にし、1つのトランザクションで書き込む。「移行済み」と日時を記録する
    4. v1 の DB は消さない。設定画面に「旧データを削除」を置くのは、v2 が安定してから
  - v1 の JSON エクスポートの読み込みも、同じ変換関数を通す
  - テスト: v1 のデータを fake-indexeddb に入れて移行し、結果を確かめる。v1 のエクスポート JSON の実物（利用者のものではなく、作ったもの）でも確かめる
- 何を引き継ぐか

| v1                           | v2 での扱い                                                            |
| ---------------------------- | ---------------------------------------------------------------------- |
| `logs`（日付・分・内容）     | 「旧記録」として読むだけの一覧。合計時間を「これまで ◯時間」として出す |
| `weeks` の `memo`・`repoUrl` | **利用者が書いた文章なので必ず残す**。旧記録の画面で読めるようにする   |
| `skills` のチェック          | 旧記録に残す。新しい進み具合には使わない                               |
| `badges`                     | 旧記録に「旧バッジ」として残す                                         |
| `settings` のテーマ          | 引き継ぐ。目標時間・休止期間は使わない                                 |
| `months`・`steps`            | 旧記録の表示に使うだけ                                                 |

- エクスポートの形: `app: 'java-study-tracker'`、`schemaVersion: 2`。読み込みは 1 と 2 の両方を受け付ける

## 7. 3案を組み合わせる場合のアーキテクチャ（概略）

### 7-1. 組み合わせ方

- 世界観は1つに決める（港・RPG・ダンジョン）。これは利用者の好みで決めること
- 技術としては、世界観は「見た目の皮」にして、データと判定には持ち込まない（後で変えられるように）
- 見た目の出力は **A の「文字の出力をそのままタイルで描く」を基本**にする
  - 独自の API が要らない。手元のターミナルでも同じ文字が出る。判定は文字列の比較で済む
  - 色やアニメーションが必要になったら、C の `@` で始まる行の決まりを後から足す（行の頭は `@@jq ` のような、学習者が書きそうにないものにする）

### 7-2. 画面

| 画面     | 中身                                                                                                                                                            |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ホーム   | 「次の1問」ボタン（開いたらすぐ問題文が見える）、持ち時間の選択（押さなくてよい）、完走見込み（小さく）                                                         |
| 問題     | 問題文／エディタ／実行／テスト結果（灯り）／出力（文字とタイル）／ヒント3段／質問文を作る／手元で実行。予想・選択・並べ替えは、エディタの場所に答える部品が入る |
| 手元課題 | 段階の一覧、作業フォルダのダウンロード、クリアコードか出力を貼る、`#/clear/<コード>` の受け取り                                                                 |
| 図鑑     | 文法カード、エラーの説明（出会ったもの）                                                                                                                        |
| 作品     | クリアした問題の出力（タイル）と自分のコード                                                                                                                    |
| 記録     | 自動で記録した時間、旧記録（v1）                                                                                                                                |
| 設定     | テーマ、エクスポート・インポート、移行の状態、Java の実行環境の状態（ダウンロード済みか、対応ブラウザか）、ライセンス                                           |

### 7-3. データモデル（IndexedDB `java-study-tracker-v2`）

| 表         | 主な項目                                                                                                                                          |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `progress` | 問題 ID、状態（未着手・挑戦中・クリア）、初クリア日時、答えを見たか、最高のヒント段階                                                             |
| `attempts` | ID、問題 ID、日時、結果（通過・失敗・コンパイルエラー・実行時エラー・時間切れ）、通過数／全体、かかった秒数、実行場所（ブラウザ・手元・実行なし） |
| `drafts`   | 問題 ID、コード、更新日時                                                                                                                         |
| `reviews`  | 問題 ID、ライトナーの箱、次の期限（余力があれば）                                                                                                 |
| `sessions` | ID、開始、終了、画面が見えていた秒数、種類（アプリ・手元課題）                                                                                    |
| `dex`      | エラーの ID、初めて出た日時、問題 ID、直した日時、メモ                                                                                            |
| `notes`    | 「分かったこと」の1行（余力があれば）                                                                                                             |
| `legacy`   | v1 のデータをそのまま（検査済み）                                                                                                                 |
| `meta`     | スキーマの版、教材の版、v1 から移行した日時、設定                                                                                                 |

- 問題 ID は意味のある固定の文字列（例: `ch02.lighthouse`）。番号（`2-4`）にしない。並び順は教材側で持つ
- 教材を直しても ID は変えない。中身が大きく変わったら教材側の `rev` を上げるだけで、クリアの記録は残す

### 7-4. 教材のファイル形式

- **Java は JSON の文字列に入れず、本物の `.java` ファイルにする**
  - 理由: エスケープの間違いがなくなる。そのままコンパイル・実行・整形の検査ができる
- 1問＝1フォルダ

```

  expected.txt    # JDK の出力から作る。手で書かない
  wrong/          # よくある間違い（CI で落ちることを確かめる）
    OffByOne.java
```

- `problem.md` の前書きの例

```yaml
id: ch02.lighthouse
type: implement # predict / fill / fix / implement / draw / parsons
title: 灯台を描く
concepts: [for, string-repeat]
```

- 判定の共通クラス（`java/harness/`）を1つ用意し、ブラウザ・手元・CI のすべてで同じものを使う

   - 質問文を作る（コピーして claude.ai を開く）
   - よく出るエラー 10種ほどの日本語の説明（英語と日本語の文言の両方に対応）
   - 手元課題（作業フォルダの zip、クリアコードか出力を貼る）
   - 7日以上空いたときの迎え方（易しい1問から。責める表示なし）
   - 時間の自動記録、旧記録の閲覧
4. **教材**: 第0〜2章（小問 約30問、手元課題 2本）。すべて CI 通過＋レビュー済み
5. **品質**: lint・型チェック・テスト・ビルド・教材の検証・Playwright の通しテストが CI で通る。README の更新

### 8-2. 余力があれば（MVP の後、上から順に）

1. 第3章以降の教材（常に2章先まで）
