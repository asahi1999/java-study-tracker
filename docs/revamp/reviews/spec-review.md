## 1. 高

### H-1. 勉強を始められる日が遅すぎる。日程の前提と合わない

- どこ
  - 03-design.md 13章（実装フェーズ）
  - 02-requirements.md 7-1（章ごとの「週3時間での目安」）
- 問題
  - フェーズ0〜3はすべて土台（確認、教材の検証、Worker、DB と移行、v1 の削除）。学べるのは早くてもフェーズ4の途中
  - 7-1 の目安は「第0章 〜11/30」「第1章 〜12/7」。今日は 11/27 で、まだ何もない。日付が最初から成り立っていない
  - critic-user.md 5-1 の一番の警告「アプリを作る時間が勉強を食う」「第0章だけの最小のページを数日で出す」に、フェーズの順番が応えていない
  - 13章の救済案「revamp ブランチの `npm run dev` で始める」は弱い
    - 毎回開発サーバーを立てるのは「1回が重い」（壁1）そのもの
    - localhost は別オリジンなので、そこで解いた記録は本番（`asahi1999.github.io`）に移らない。エクスポート・インポートはフェーズ3まで無い
- 直し方
  - 「縦の薄い切り口」を先に作るフェーズを、フェーズ1と2の間に入れる
    - 中身: teavm-javac の同梱、Worker 1組（時間切れだけ）、出力の比較だけの判定、ステップ画面1つ（エディタ＋実行＋松明）、第0章の5〜8問、`progress` と `drafts` の2表だけ
    - 削るもの: 図鑑・レベル・宝箱・見込み・作品・旧記録・PWA・手元課題（すべて後のフェーズ）
    - 完了の条件: 利用者が第0章を最後まで解ける
  - 公開の仕方を、利用者に先に決めてもらう（確認待ち）
    - 案A: 縦の切り口の時点で main に出す（v1 の DB には書かないので v1 は壊れない。ただし v1 の画面は消える）
    - 案B: MVP まで出さず、その間は v1 も使わない（実質、勉強しない期間になる）
  - 7-1 の日付は、フェーズ0のあとで「縦の切り口が出る日」から引き直す。2月末に収まらないなら、おかわり（`optional`）と第9章の段階数で調整する

### H-2. v1 の移行に失敗したときの逃げ道が、公開後は使えない

- どこ
  - 03-design.md 3-3（移行の手順、「失敗したら…エクスポートした JSON から移せます」）
  - 02-requirements.md F-DATA-1・F-DATA-2、N-DATA-3
  - 00-brief.md「無理な部分はエクスポート（JSON）経由で移せるようにする」
- 問題
  - v2 は同じ URL で v1 を置き換える。公開した時点で v1 の画面は無くなるので、v1 から JSON を書き出す手段が無い。設計の逃げ道は使えない
  - `meta.migration` があれば何もしない、と書いてある。`failed` も含むので、一時的な失敗（DB が使用中など）でも二度と自動で試さない
  - 本物の v1 データは本番のオリジンにしかない。CI・開発サーバーでは、作ったデータでしか試せない
  - v1 は初回起動でロードマップを自動で入れる（`src/db/seed.ts`）。v1 を一度でも開いた人は、必ず「旧記録あり」になる。「旧記録があればトースト」の「ある」の決め方が無い
- 直し方
  - 公開前の手順に入れる（13章、フェーズ6の完了条件）: 「main に出す前に、v1 の設定画面から JSON を書き出して保管する」。利用者がやること
  - その JSON を、開発環境で v1 形式のインポート（`schemaVersion: 1`）として通し、旧記録の画面で読めることを確かめる。実データでの移行の予行になる
  - `status: 'failed'` のときは、起動のたびに再試行する（`done`・`not-found` のときだけ止める）。設定画面に「v1 のデータから読み直す」ボタン
  - v1 の Zod を通らなかったときも、読めた分（`raw`）をエクスポートに入れる（3-2 にある）。加えて設定画面から「v1 の生データを JSON で保存」できるようにする
  - 「旧記録あり」の条件を決める: `logs` が1件以上、または `weeks` の `memo`・`repoUrl` が空でない、または `skills` にチェック済み、または `badges` が1件以上

### H-3. Safari の「Dock に追加」は保存領域が別かもしれない（自信がない）

- どこ
  - 02-requirements.md 4-1 の 6（3ステップ後にインストールのカード）、F-SETUP-1、F-DATA-1、2章「ブラウザは Chrome か Safari（どちらが主かは未定）」
  - 03-design.md 15章（未確認の一覧にこの項目が無い）
- 問題
  - macOS の Safari で「Dock に追加」した Web アプリは、Cookie やサイトのデータを Safari と共有しない、と記憶している（**自信がない**。Apple のサポート記事で確かめる）
  - もしそうなら
    - Safari のタブで3ステップ解いたあと Dock に入れると、Dock 側では進み具合が0に見える
    - v1 の DB は Safari 側にある。Dock 側では `not-found` になり、旧記録が移らない
    - 手元課題の `#/clear/` のリンク（後続）は既定のブラウザで開くので、Dock 側に記録されない
  - Chrome のインストール版はプロファイルと保存領域を共有するので、この問題は起きない（はず）
- 直し方
  - フェーズ0の確認項目に足す: Safari のタブで IndexedDB に書く → Dock に追加 → Dock 側で読めるか
  - 別だった場合の方針を先に決める（まとめ役の判断）
    - 案A: 主ブラウザを Chrome に推奨し、準備の手順もそれに合わせる
    - 案B: Safari のときは、インストールの案内を最初の1ステップより前に出し、「Dock から開く」で始めてもらう。v1 の移行は「Safari のタブで JSON を書き出して Dock 側で読む」手順を案内する
  - どちらにしても、利用者の主ブラウザをフェーズ0で聞く（critic-user.md 5-8 の未決事項）

### H-4. 貼った出力の判定が「うっかり通る」「うっかり読めない」

- どこ
  - 03-design.md 5-4（判定の行）、5-6（`JqCheck.java`）、6-7（`Check.java` の出力）
  - 02-requirements.md F-STEP-10、F-PROJ-3
- 問題
  - `hello` の行は `{"t":"hello","v":1,"source":"compact"}` だけで、どの問題か・どの版かが入っていない。別の問題（たとえば1つ前の問題）の `JqCheck.java` の出力を貼っても、`done` の passed = total なら合格になる。コピー元を間違えるのはよくある
  - 手元で貼った出力では `\u001E` が消えることがあるので `@@jq ` だけでも受け付ける、とある。一方で、ターミナルでは標準出力と標準エラーが混ざる。学習者が `System.out.print("###")`（改行なし）で終わると、次の判定の行は `###@@jq {...}` と同じ行に出る。行頭で探すと読めず、`done` が無い扱い（crash・exited-early）になる
  - ブラウザでも同じ。学習者の `System.err.print`（改行なし）のすぐ後に判定の行が続く
  - 合格の条件に「total ≥ 1」が書いていない。`tests` モードで段階の番号がずれると 0/0 になり、合格に見える
- 直し方
  - `hello` と `done` に `step`（問題 ID）、`rev`、`tests`（Tests.java とケースのハッシュの先頭8文字）を入れる。アプリは貼られたものが今の問題・今の rev と一致するときだけ記録する。rev だけ違うときは「古い版の判定です」と出し、記録するか選べる
  - ハーネスは判定の行を書く前に、その流れ（stdout・stderr）の最後の文字が改行でなければ改行を足す
  - 読む側は、行の途中にある `@@jq ` も受け付ける（`\u001E` があればそこから、無ければ最後の `@@jq ` から）
  - 合格は「`done` があり、total ≥ 1 で、passed = total」と明記する。content-verify でも「Solution の total が 1 以上」を確かめる
  - `Check.java` の出力も同じ。先頭の `JQ-CHECK 1 p03 rev1` と、開いている課題が一致しないときは記録しない

### H-5. 教材の検証で「間違いの解答が落ちる」が空振りする

- どこ
  - 03-design.md 6-4（Starter・wrong の検証）、6-9 の表（Starter、wrong/*.java）
- 問題
  - 「wrong はそれぞれ少なくとも1つ失敗」「Starter は少なくとも1つ失敗」とだけある。コンパイルエラーも「失敗」に数えると、打ち間違いのある wrong ファイルでも検証が通る
  - すると「テストが弱すぎない」（critic-tech.md 3-2 の簡易ミューテーションテスト）が確かめられない。弱いテストのまま公開され、学習者の間違ったコードが合格する（うっかり通る）
  - 穴埋め・実装・絵の Starter がコンパイルできないと、学習者の最初の実行が意図しないエラーになる。図鑑の「発見」も意図せず起きる
- 直し方
  - wrong は「コンパイルが通り、実行が終わり、テストかケースで少なくとも1つ失敗」を条件にする。コンパイルエラーを見せたい間違いは `fix` の Starter で扱う
  - fill・implement・draw の Starter も「コンパイルが通り、テストかケースで失敗」を条件にする（コンパイルエラーで始める問題にしたいなら `expectError` を書く）
  - 加えて「別解」フォルダ `alt/*.java`（任意、implement・draw は1つ以上を推奨）を置き、全部通ることを確かめる。テストが模範解答に寄りすぎていないか（出力の書式を問題文より厳しく見ていないか）を検出できる。critic-tech.md 3-2 の「穴埋めの別解」がこれで設計に戻る

## 2. 中

### 01-decisions.md・00-brief.md との食い違い

#### M-1. 最小単位「1〜3分」が守られていない

- どこ: 03-design.md 6-2（`minutes: 1〜5`）、02-requirements.md 7-1（「学習者は1.5〜2倍かかる前提で小問は7分で計算」）、1-3 のホーム「約3分」
- 問題
  - 01-decisions.md は「最小単位は1〜3分」。スキーマの上限が5で食い違う
  - 作り手の見積もり3分を出しつつ、実際は7分かかる前提で日程を組んでいる。ホームの「約3分」が毎回はずれると、「1回が重い」に戻る
  - 実装問題（「ダメージ計算」「入力を受けて表示」）が1〜3分に収まるかが疑わしい
- 直し方
  - スキーマの上限を3にする。収まらない実装問題は2ステップに分ける（前半: メソッドの形、後半: 中身）
  - ホームの目安は `minutes × k`（9-7 の実際の倍率）を出す。k が決まるまでは `minutes` のまま

#### M-2. 手元課題の段階の長さが、要件の中で食い違う

- どこ: 02-requirements.md F-PROJ-2（15〜25分）と 7-3 第9章（p09 は「5段階、各約50分」）、03-design.md 9-8（初期値の上限120分）
- 問題: p09 だけ1段階50分。週ごとのばらつきが大きい利用者には、50分の塊は始めにくい
- 直し方: p09 を10段階前後（各20〜25分）に分ける。段階の数を増やしても、クリアコードの仕組みはそのまま使える

#### M-3. 「手元の準備」がコースの並びに入るのか入らないのか

- どこ: 02-requirements.md 4-1 の 7（「第0章の最後に手元の準備ステップ」）と、03-design.md 9-1（「手元課題の段階はコースの並びに入れない」）。p00 は手元課題として定義されている（6-6）
- 問題: 9-1 のままだと、ホームの「次の1ステップ」に手元の準備が出てこない。第1章の手元課題 p01 で初めて zip の話になる（critic-user.md が「一番重い1回」とした場面）
- 直し方: p00 だけは例外としてコースの並び（第0章の最後）に入れる、と 9-1 に書く。または「第0章を終えたらホームの手元課題の枠を目立たせる」と明記し、4-1 の 7 を直す

#### M-4. 宝箱の飾りが「3つ目の収集」になっている

- どこ: 03-design.md 6-5（`decorations.yaml`）、9-5（「まだ持っていないものから選ぶ」「全部持っていれば空っぽ」）、F-WORK-2
- 問題: 01-decisions.md は「収集は2つだけ（技カードとエラー図鑑）」。持っていない飾りから選び、全部そろうと空になる、は集める仕組みそのもの
- 直し方: 飾りは数を数えない・一覧に「？」を出さない、と決める。中身は「宝箱の等級ごとに決まった飾りを、作品の次の空き場所に置く」程度に簡単にする。MVP では等級1種でもよい

#### M-5. 完走見込みが、遅れの警告と同じ働きをする

- どこ: 03-design.md 9-7、02-requirements.md F-FC-1・F-FC-2（近道ルートは後続）
- 問題
  - 見込みが 2/28 を超えると「（3月は予備）」が消え、日付だけが後ろにずれる。文字の色を変えなくても、それ自体が「遅れ」の知らせになる
  - しかも MVP には近道ルート（F-FC-2）が無いので、見ても打つ手がない
  - `P` の下限30分で計算すると、見込みが「2028年」のような日付になりうる
- 直し方
  - MVP では、見込みが 2/28 を超えたら日付を出さず「おかわりを後回しにすると ◯月◯日ごろ」だけを出す（`optional` を除いた R で計算。近道ルートの切り替え機能は後続のまま）
  - 表示する日付の上限を決める（例: 3/31 を超えたら「春ごろ」）

#### M-6. 見込みの「1週の学習時間」に、使い始める前の週が入る

- どこ: 03-design.md 9-7 の `P`
- 問題: 「今週を除く直近4週」「0分の週も含める」とある。使い始めて3週目には、使う前の0分の週が平均に入り、P が半分になる。見込みが急に遠のく
- 直し方: 数える週を `meta.app.createdAt` の週以降に限る

### 要件と設計の食い違い・抜け

#### M-7. 「次のステップ」の選び方に必要なデータが無い

- どこ: 03-design.md 9-1、3-2（`Progress`）
- 問題
  - 「`trying` のうち最後に開いたもの」とあるが、`Progress` には `firstOpenedAt` しかない
  - 地図からどのステップにも飛べる（鍵なし）。のぞいただけで `trying` になると、次のステップがそこに飛ぶ
  - 難しくて放置したステップが、いつまでも「次」に出続ける。壁1に反する
- 直し方
  - `lastOpenedAt` を足す
  - `trying` になるのは「コードを変えたか実行したとき」に限る
  - 同じステップが3回続けて「次」に出て、開かずに終わったら、コースの順の次のものを出す（地図には残る）

#### M-8. 宝箱と解き直しの「まだ」を覚えておく場所が無い

- どこ: 03-design.md 9-1 の 1・2、9-5、3-2（`MetaApp.lastActiveAt`、`Chest`）
- 問題
  - `gap` は `lastActiveAt` から計算する。起動時に `lastActiveAt` を先に更新すると gap は0になる
  - 宝箱を開けずに閉じると、次の起動では gap が0で、宝箱が消える。`Chest` は開けたものしか持たない
  - 「おかえりのあとの解き直しがまだ」も保存先が無い
- 直し方
  - `meta.welcome = { pendingChestGap: number | null; pendingReview: boolean; at }` を足す
  - 起動時の順番を決める: gap を計算 → `welcome` を書く → `lastActiveAt` を更新
  - 解き直しは「飛ばす」を置く（F-REV-1 と同じ扱い）。宝箱はホームの次のステップの上に並べ、次のステップを隠さない（1-3 のワイヤーフレームの通り。9-1 の「開けたら 2. へ」と合わせる）

#### M-9. 教材の更新で、書きかけが「判定用のコードのエラー」になる

- どこ: 03-design.md 3-2（`Draft.rev`）、4-7（「判定用のファイルのエラー → 教材の不具合かもしれません」）、F-STEP-13
- 問題
  - 教材の rev が上がってメソッドの形が変わると、古い書きかけでは Tests.java がコンパイルできない。画面は「教材の不具合かも」と出す
  - rev が変わらなくても、学習者がメソッドの名前や引数を変えると同じエラーになる。こちらの方がずっと多い。「教材の不具合」と出すと、誤った報告と不信につながる
  - F-STEP-13 の「書きかけは残している」と知らせる仕組みが、設計に書かれていない
- 直し方
  - ステップを開くとき `draft.rev !== 教材の rev` なら「問題が新しくなりました。書きかけは残しています [新しいひな形と見比べる] [ひな形に戻す]」を出す
  - Tests.java・given のコンパイルエラーで、エラーが `cannot find symbol` 系なら「判定用のコードが、あなたのコードの `canMove` を見つけられません。名前や引数を変えていませんか」と出す。「教材の不具合かも」はそれ以外のときだけ

#### M-10. 教材と記録の ID を守る仕組みが無い

- どこ: 02-requirements.md F-CONTENT-5、N-DATA-5、03-design.md 6-1・6-2（`id: ch<2桁>.<slug>`、「フォルダの章と一致」）、6-6（段階の ID `p02.s1`）、`concepts.yaml`・`errors.yaml`・`decorations.yaml`
- 問題
  - 「ID は変えない」は決まりだけで、CI が守らない
  - ID に章番号が入っている。問題を別の章に移すと ID が変わり、その問題のクリア・下書き・技カードの根拠が消える
  - 手元課題の段階は番号（`s1`）。途中に段階を足すと、記録の意味がずれる
  - 技カード（`conceptId`）・図鑑（`errorId`）の ID も同じ
  - `reviewed: true` にしたあとで中身を直しても、再レビューなしで公開される
- 直し方
  - `content/ids.lock`（公開済みの問題・段階・技・エラーの ID と、レビュー時の中身のハッシュ）を置く。CI で次を落とす
    - 公開済みの ID が消えた
    - `reviewed: true` なのに、ハッシュがレビュー時と違う（直したら `reviewed` を外して再レビュー）
    - Starter・Tests・ケースが変わったのに `rev` が上がっていない
  - 章を移すときのために `aliases: [ch02.old-slug]` を前書きに持てるようにし、起動時に記録の ID を付け替える
  - 段階の ID は番号ではなく slug（`p02.walls`）にする。表示の順番は `n` で持つ

#### M-11. 「手元で実行」の往復で、コードの正本がどちらか決まっていない

- どこ: 03-design.md 5-6、F-STEP-10、F-RUN-6（非対応ブラウザでは書く問題がすべてこの道）
- 問題
  - `JqCheck.java` をコピーして VS Code で直し始めると、直したコードはアプリに戻らない。質問文の「自分のコード」、図鑑の抜粋、作品のコードが古いまま
  - コンパイルエラーのとき `@@jq` の行は出ず、`JqCheck.java:123: エラー: ';'がありません` だけが出る。この形を読む方法と、行番号の引き方（貼られた出力には先頭のコメントが無い）が書かれていない
  - 6-7 の `Check.java` の出力形式にも、コンパイルエラーのときの形が無い
- 直し方
  - 決まりを1つにする: 「コードはアプリで書く。手元は判定するだけ」。手元で直したくなったら、貼る欄の横に「直したコードも貼る」欄を置く
  - アプリは `JqCheck.java` を作るときに、学習者のコードの開始行を `Draft` 側に覚えておく。javac の `ファイル名:行:` を読んで引く
  - `JqCheck`・`Check` ともに、コンパイルエラーのときの出力形式を決める（例: `JQ-COMPILE <ファイル>:<行>: <文言>` を1行ずつ）。図鑑の日本語の文言の判定はこれを使う

### Java の実行・判定

#### M-12. 教材の検証の時間切れ（10秒）と、画面の時間切れ（既定3秒）が違う

- どこ: 03-design.md 6-9（「1回の実行の上限: JDK・teavm とも10秒」）、4-4（問題の `timeoutMs`）
- 問題: 模範解答が teavm で4秒かかっても検証は通る。画面では「終わらない（無限ループかも）」になり、図鑑に `infinite-loop` が「発見」される。正しいコードが落ちる
- 直し方
  - content-verify で、teavm（Node）の実行時間が `timeoutMs` の 1/3 以下であることを確かめる（遅い PC の余裕）
  - 画面の時間切れは「run.worker が `main` を呼ぶ直前」から測る、と明記する（Wasm の読み込みを含めない）

#### M-13. 学習者が JDK と結果が違う書き方をしても、気づけない

- どこ: 02-requirements.md 8-3、03-design.md 6-9（禁止リストは教材だけを検査）
- 問題
  - 禁止リスト（`HashMap`、`Random`、`getMessage`、`%e`、拡張 for 中の `remove` など）は教材にしかかからない。学習者は知らないので普通に書く。特に「答えも」でチャットからもらったコードには `HashMap` がよく入る
  - するとブラウザだけで落ちる、またはブラウザだけで通る。どちらも「うっかり」
- 直し方
  - 実行前に TypeScript で学習者のコードを同じ正規表現で見て、当たったら結果の下に「この書き方はブラウザと本物で結果が変わることがあります（HashMap の順番）。おかしいと思ったら手元で」と出す。判定は変えない
  - 禁止リストの正規表現を `java/test-vectors/` 相当の共通データにし、content-verify と画面で同じものを使う

#### M-14. コンパクトソースの問題に `public class Main` を貼ると、分かりにくいエラーになる

- どこ: 03-design.md 4-5（外枠）、10-1（「答えも」）
- 問題
  - 第0〜3章は `final class Main { ... }` で包む。チャットからもらった `public class Main { public static void main(...) }` を貼ると、`Main` の中に `Main` ができてコンパイルエラーになる。文言は学習者には意味が分からない
  - 質問文を作る機能がある以上、よく起きる
- 直し方
  - `source: compact` の問題で、学習者のコードの一番外に `class` 宣言や `static void main(String[]` があれば、包む前に止めて「この問題は `void main()` の形で書きます。`public class Main { ... }` の外側を外してください」と出す
  - 質問文の「今の学習段階」に「`void main()` の形（コンパクトソース）で書いている」を必ず入れる

#### M-15. Scanner の代わりが、JDK と同じ動きをするかの検証が無い

- どこ: 03-design.md 4-6、6-9（Solution しか動かさない）
- 問題
  - 第1章の `Scanner` は初心者のつまずきの中心（`nextInt()` のあとの `nextLine()` が空文字を返す、入力が尽きたときの `NoSuchElementException`、`InputMismatchException` のあと字句を消費しない など）
  - 模範解答はこうした道を通らないので、content-verify では違いが見つからない。学習者だけがブラウザと手元で違う動きを見る
  - `static Scanner sc = new Scanner(System.in)` と書くと、JDK 側（`System.setIn` をケースごとに差し替え）は2件目以降で古い入力を読み、ブラウザ側（`setInput`）は新しい入力を読む、という違いも起きうる（自信がない。実装次第）
- 直し方
  - フェーズ1に「Scanner の適合テスト」を足す: 入力と呼び出しの並び（`nextInt`→`nextLine` など）を30組ほど用意し、JDK の本物と代わりのクラスの結果（戻り値・例外の型）が一致することを CI で確かめる
  - ケースごとに `static` が持ち越される件は、ケースごとに別の実行にするか（遅くなる）、「`static` な Scanner は使わない」を問題文の決まりにするかを決める

#### M-16. `double` の表示が JDK と同じかの確認が無い（自信がない）

- どこ: 02-requirements.md 8-3、03-design.md 15章
- 問題: 第1章から `double` を使う。JDK 19 以降は `Double.toString` の桁の出し方が変わった。TeaVM の実装が、すべての値で同じ桁を出すかは確かめていない（**自信がない**）。研究で一致を見たのは限られた値だけ
- 直し方: フェーズ0か1で、`0.1+0.2`、`1.0/3`、`100.0/7`、`1e7`、`1e-4`、`(double) 1/3*3` など100値ほどを JDK と teavm で `println` して比べる。違いがあれば、8-3 に「`double` は `printf("%.2f")` で出す」を足し、content-verify で検査する

#### M-17. `Check.java` の子プロセスが、出力の多いコードで止まる

- どこ: 03-design.md 5-5（手元課題）、6-7（「標準エラーの `@@jq` の行を読む」）
- 問題
  - 子プロセスの標準出力を読まずに標準エラーだけ読むと、学習者が大量に出力したとき、出力の管（パイプ）が詰まって子プロセスが止まる。20秒の時間切れまで何も出ない
  - 手元には出力の上限が無い。無限に出力するコードは、ターミナルと貼り付けを埋める
- 直し方
  - 標準出力と標準エラーを別スレッドで最後まで読む（または `redirectOutput` でファイルに出す）
  - ハーネス（`JqCapture`）に出力の上限（ブラウザと同じ10万文字・2,000行）を入れ、超えたら `{"t":"limit"}` を出して終わる。ブラウザ・手元・CI で同じ動きになる
  - 判定の行の `actual` は 20KB で切る（「…（省略）」を付ける）

### PWA・オフライン

#### M-18. 初回の先読みが Service Worker のキャッシュに入らない

- どこ: 03-design.md 11-1（`registerType: 'prompt'`）、11-2（「先読みで fetch したものがそのままキャッシュされる」）、N-OFF-2
- 問題
  - 初回の訪問では、Service Worker の登録が終わってもページはまだ Service Worker の管理下にない（`clientsClaim` が無いため）。その間に作った Worker の `fetch` も管理下にない
  - すると初回にダウンロードした約7.6MB は、実行時のキャッシュに入らない。2回目にもう一度ダウンロードし、それまではオフラインで動かない。設定画面の「保存済み」も出ない
- 直し方
  - teavm-javac のファイルは Service Worker に任せず、アプリが自分で Cache Storage に入れる（`caches.open(名前).put()`）。読み込みも先にそこを見る。Service Worker の有無に関係なく、初回のダウンロードでオフラインに備えられる
  - または `clientsClaim: true`（初回のインストールだけ効く。書いている途中の再読み込みは起きない）。どちらにするかをフェーズ5の前に決める
  - 12-2 の Playwright の4本目を「初回訪問 → 先読みが終わる → オフライン → 再読み込み → 実行できる」に変える（2回目を挟まない）

### 教材の検証（content-verify）

#### M-19. 期待する出力が、問題文と合っているかを誰も確かめない

- どこ: 03-design.md 6-11（公開までの流れ）、6-4（`expected` は JDK の出力から作る）
- 問題

#### M-20. 「使ってよい文法」の検査が、問題文・ヒント・解説・given に効かない

#### L-10. 外枠で列がずれるのは1行目もある

- どこ: 03-design.md 4-5
- 問題: import が無いとき、1行目に `import module java.base; ` と ` final class Main {` の両方が入る。「ずれるのは class を足した行だけ」は不正確。コメントや文字列の中の `import ...;` を最後の import と取り違える可能性もある
- 直し方: `wrap.json` のテストデータに「import なし」「コメントの中の import」「テキストブロックの中の import」を入れる

#### L-11. 対応ブラウザの版を、確かめる前に画面の文言に書いている

- どこ: 02-requirements.md N-BR-2（「Chrome 119・Safari 18.2・Firefox 120 以降で」）
- 問題: 版は WasmGC の対応表から引いただけ。teavm-javac が使う例外処理の方式によっては、もっと新しい版が要る（未確認）
- 直し方: 文言は「最新の Chrome か Safari で開くか」にし、版はフェーズ0の結果で設定画面の説明にだけ書く

#### L-12. Issue 作成の URL の長さ

- どこ: F-STEP-12
- 問題: 自分のコードを URL の引数に入れると、長いコードで URL が長すぎて開けないことがある（上限は確かめていない）
- 直し方: 本文は 6,000文字で切り、「全文はクリップボードに入れました。貼ってください」と出す

#### L-13. deploy.yml を変えないなら、ビルドに JDK を使えない

- どこ: 03-design.md 12-3（「deploy.yml は変更なし」「`npm run build` が `workspace:build` を含む」）
- 問題: deploy.yml には `setup-java` が無い。workspace-build が JDK を呼ぶと公開が壊れる
- 直し方: 「content-build と workspace-build は JDK を使わない。JDK が要るもの（`jq-shim` の .bin）は生成してコミットする」と 6-7・6-8 に明記し、`check` ジョブ（JDK なし）で `npm run build` が通ることで守る

#### L-14. zip の中の `mvnw` の実行権限

- どこ: 03-design.md 6-7（`fflate` で zip を作る）、p09
- 問題: zip に実行権限を入れないと、展開後の `./mvnw` が「許可がありません」になる（macOS の展開で権限が残るかは確かめていない）
- 直し方: fflate の外部属性で 0755 を付ける。手順には `sh mvnw` でも動くと書く

#### L-15. 細かい食い違い

- `JqCheck.java` の `class` の形を確かめる時期: 13章はフェーズ0、15章はフェーズ1
- 手元課題の段階の合計: 9-2 は29、7-3 から数えると p00(1)＋p01〜p08(各3)＋p09(5)＝30（M-2 で p09 を分けるとさらに変わる）
- `THIRD_PARTY_NOTICES.md` の置き場: 01-decisions.md は `public/java/teavm-javac/<版>/` のそばに読める書き方、03-design.md はリポジトリ直下。直下で問題ないが、どちらかに合わせて明記する
- 作品の「今の版」の決め方（どの条件で v0.2 → v0.3 になるか）が書かれていない
- 「そのまま実行」（段階0）が `mode: output` のとき松明に数えるのかがあいまい。8-1 の目標の絵が `expected/1.txt` か `0.txt` かもこれ次第

#### L-16. 長く使ったときの compile.worker

- どこ: 03-design.md 4-2
- 問題: 毎回 `createCompiler()` で作り直しても、1つの Wasm インスタンスのメモリは減らないかもしれない（研究では13回まで）
- 直し方: 50回ごと、またはメモリが一定を超えたら Worker を作り直す。M-21 の Safari 50回の確認で決める

#### L-17. 学習時間の二重計上

- どこ: 03-design.md 9-8
- 問題: PWA とブラウザのタブを両方開いていると、両方が数える
- 直し方: `BroadcastChannel` で、操作のあった方だけが数える。MVP では「既知の制限」として README に書くだけでもよい
